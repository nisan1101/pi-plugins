# What `/new` does to Scheduled Wake timers (Pi 0.84.2)

## Verdict

A **successful** `/new` cancels every still-pending runtime timeout in the old Scheduled Wake extension instance and clears that instance's `pendingWakes` Map. It deliberately does **not** append an empty checkpoint to the old session. The new session gets a newly loaded extension instance with an empty Map, an empty session history, and no restored timers. If the old session is later resumed, its newest unresolved checkpoint is converted into one visible `scheduled-wake-cancelled` message with `triggerTurn: false`; its timers are never rearmed, even if their deadlines are still in the future. Therefore no old timeout can fire *after normal cleanup has run*. A timeout callback can still win a race and run **before** its shutdown handler clears it; that callback remains bound to the old session, never the new one.

## Exact lifecycle ordering

1. Interactive `/new` calls `runtimeHost.newSession()` (`.../dist/modes/interactive/interactive-mode.js:2420-2423`, `:5282-5294`).
2. `AgentSessionRuntime.newSession()` first awaits old-runtime `session_before_switch { reason: "new" }`. If any handler cancels, it returns immediately: no `session_shutdown`, no new session, and Scheduled Wake's old timers continue normally (`.../dist/core/agent-session-runtime.js:147-151`; event dispatch/cancellation is sequential in `.../dist/core/extensions/runner.js:579-596`). Scheduled Wake itself registers no `session_before_switch` handler.
3. Pi allocates a fresh `SessionManager`, then tears down the old runtime (`agent-session-runtime.js:152-160`). Teardown first aborts and waits for an active agent run to settle, then awaits `session_shutdown { reason: "new", targetSessionFile }`, then invalidates/disposes the old session (`agent-session-runtime.js:102-112`; abort/wait at `.../dist/core/agent-session.js:1165-1178`).
4. Scheduled Wake's old `session_shutdown` handler synchronously calls `clearTimeout()` for every Map value and clears the Map (`packages/pi-scheduled-wake/extensions/scheduled-wake.ts:143-146`). It writes no checkpoint.
5. Pi creates/applies the replacement runtime with `sessionStartEvent { reason: "new", previousSessionFile }`, rebinds it, and then emits the new instance's `session_start` (`agent-session-runtime.js:161-172`, especially `finishSessionReplacement` at `:120-126`; actual emission in `.../dist/core/agent-session.js:1741-1762`). This matches the installed lifecycle documentation (`.../docs/extensions.md:316-320,415-432`).

## Runtime memory and persisted state

- Each extension factory invocation owns one closure-local `Map<string, RuntimeWake>` (`scheduled-wake.ts:60-61`). Scheduling creates a timeout, stores `{ wake, timer }`, then appends a **complete** `scheduled-wake-state` snapshot (`:90-103`; snapshot helper `:63-67`).
- Timeout expiry only calls `pi.sendMessage(..., { triggerTurn: true, deliverAs: "followUp" })`; it does **not** delete the Map entry (`:91-101`). The wake remains recoverable until the custom wake reaches `message_end`; only then does the plugin delete it and append the new complete snapshot (`:137-140`). The test codifies this delivery boundary (`test/scheduled-wake.test.mjs:99-118`).
- `pi.appendEntry()` becomes a branch-local custom entry; Pi's `SessionManager.appendCustomEntry()` advances the leaf and persists through `_appendEntry()` (`.../dist/core/session-manager.js:754-758,819-830`). Custom entries persist but do not enter model context (`.../docs/extensions.md:1412-1429`; session format `.../docs/session-format.md`, symbol `CustomEntry`, lines 292-301).
- Shutdown intentionally leaves the latest old checkpoint untouched. The spec states this explicitly (`SPEC.md:88-93`), and the fake-timer test verifies that advancing time after repeated shutdown emits nothing (`test/scheduled-wake.test.mjs:242-254`). Thus old JSONL evidence survives while timeout handles and the Map do not.
- The replacement `SessionManager` contains only a new header, cleared indexes, and `leafId = null` (`.../dist/core/session-manager.js:645-665`). `/new` does not copy old entries or set `parentSession` unless an API caller explicitly supplied that option (`agent-session-runtime.js:154-165`). The newly invoked Scheduled Wake factory therefore starts with an empty Map, and its `session_start` scan finds no wake marker.

## Later resuming the old session

The fresh extension instance loaded for the resumed old session walks backward from that session's active leaf and stops at the newest valid `scheduled-wake-state` or `scheduled-wake-cancelled` marker (`scheduled-wake.ts:38-57`). If the shutdown-preserved snapshot is non-empty, `session_start` sends one visible cancellation message listing reasons and original deadlines, with `details.pending: []` and `triggerTurn: false` (`:113-135`). That message participates in future model context but does not start an unsolicited turn; Pi's delivery contract is at `.../docs/extensions.md:1390-1407` (`pi.sendMessage`, `deliverAs`, `triggerTurn`). The empty pending marker prevents repeat notices on subsequent resumes. The behavior is tested at `test/scheduled-wake.test.mjs:121-146`.

No deadline comparison occurs during recovery, and no `setTimeout()` occurs in `session_start`, so future-due and overdue wakes are treated identically: report interruption, never restore. The spec expressly excludes persistent timers across crash/resume/session replacement (`SPEC.md:88-95,134-141`). Managed jobs or remote targets are not stopped or inspected.

## Races and crash edges

- **Timer vs. `/new`:** `session_before_switch`, abort settling, and extension shutdown dispatch are awaited and can yield. While the old Scheduled Wake shutdown handler has not yet run, its timeout is still live. A callback that wins first sends only through its captured old `pi`; it cannot migrate to the replacement session. If its custom message reaches `message_end` first, the old session gets an empty snapshot and later resume has nothing to cancel. If it was fired/queued but not delivered when shutdown wins, the old non-empty checkpoint remains and resume reports it interrupted. The source/test deliberately keeps fired wakes pending until delivery (`scheduled-wake.ts:91-103,137-140`; test `:99-118`).
- **During `session_shutdown`:** handlers run sequentially and are individually awaited (`runner.js:579-608`). A timeout can therefore run while an earlier async shutdown handler yields, before Scheduled Wake's own handler. Once Scheduled Wake's synchronous handler executes, all not-yet-run callbacks are cleared and the Map is emptied. An already-started send/agent action may briefly race old-session disposal, which aborts and invalidates the old runner (`agent-session.js:556-570`), but it cannot become a new-session timer or message.
- **Cancelled switch:** if `session_before_switch` returns `{ cancel: true }`, teardown never begins; the old timeout and Map remain active (`agent-session-runtime.js:147-151`).
- **Hard crash before or during switch:** process death destroys all in-memory handles regardless of whether `session_shutdown` ran. Any checkpoint successfully written to the old session remains the recovery source. A crash before the cancellation marker is appended can cause the interruption notice to be attempted again on the next resume; a crash after the empty cancellation marker persists does not. No timer is reconstructed after restart.
- **Checkpoint/write failure:** scheduling installs the timeout and Map entry *before* calling `persistPendingWakes()` (`scheduled-wake.ts:91-103`). If that synchronous append throws, a live runtime timer can exist without a durable checkpoint until shutdown/process death. Conversely, `message_end` deletes from the Map before appending the empty snapshot (`:137-140`); if that append fails, the stale non-empty checkpoint can make a later resume conservatively report a wake as interrupted even though delivery occurred. Pi reports extension errors rather than retrying; the plugin spec records this policy (`SPEC.md:95`).
- **Crash after old teardown but before replacement startup:** old handles are already gone and its unresolved checkpoint is still intact. The newly allocated session may exist only in memory until Pi flushes it; `SessionManager` delays initial file creation until persistence conditions are met (`session-manager.js:645-668,724-752`). Resuming the old session later still performs the cancellation flow above.
